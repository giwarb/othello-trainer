# T202: 中盤練習の結果画面: 評価値・グラフ・損失を同じ基準で一貫させる(深さ偶奇の統一)

## 目的
中盤練習の結果画面で「評価値 -3 → +2(損失0石)」と表示される一方、グラフは0から始まって-2付近で終わる、という **互いに食い違う表示** を解消する。ユーザーが見て納得できる、一貫した評価値・グラフ・損失にする。

## 背景・コンテキスト
### ユーザー報告(2026-10-16、本番Pages、中盤練習 問題86)
f2 → (AI応手) → f1 → (AI応手) → e1 → (AI応手) と打った結果画面: 「クリア! ★★★」「評価値 -3 → +2(損失0石)」「1〜3手目すべて最善手」。グラフ(7点)は 0, -2.75, -2.75, -0.10, -0.49, -0.31, -2.26。ユーザーの疑問: 相手の応手で終わっているのか/-3→+2なのにグラフ最後は-2付近/-3→+2なら差は+5なのに損失0石?/グラフは何を表すのか。

### 調査結果(explorer、node+wasmで本番設定を再現し同じ値を確認)
符号の反転漏れやパス起因のバグは **なし**。次の3つが重なっている。

1. **深さの偶奇による評価の振れ(根本)**: 同じ局面でも探索深さで評価が大きく振れる。問題86の終了局面(黒番)の最善手の評価: d6=+0.67 / d7=+0.79 / d8=-2.26 / d9=+2.29 / d10=-1.28 / d11=+5.04 / d12=+1.61。白c2後の局面: d8=-2.75 / d9=-0.10 / d10=-0.49 / d11=-0.31 / d12=-2.26。
   - 現行の allMoves+maxNodes 経路(T201で導入、`engine/src/search.rs`・`engine/src/protocol.rs`)は「全ルート手を同一深さで一巡し、ノード予算内で完走した最深ラウンドを採用」する。予算 240万ノードでは局面により d10 だったり d9 だったりし、**解析ごとに完走深さの偶奇がばらばら** になる。
   - さらに、根の深さ d の解析で手 m の値は「m を打った後の局面を d-1 で探索した値」。ユーザー手番の局面の解析から得た値と、相手手番の局面の解析から得た値では、探索末端で手番を持つ側が逆になる。そのため、相手の応手の評価値をグラフに並べると、同じ深さでもジグザグになる。
2. **グラフの点の算出元が一貫していない**(`app/src/components/moveEvalTimeline.ts` の `buildEvalGraphPoints` 70-84行付近):
   - 1点目は常に固定の 0 で、開始評価ではない。
   - 2点目以降は各手の着手前局面の解析で、その手の `discDiff` を黒視点に変換したもの。相手の手の点は「相手手番局面の解析値」。
   - 最終点は相手の最後の応手の評価で、終了評価(B)ではない。
   - 縦軸は常に黒視点(`EvalGraph.tsx` 193行「黒優勢が上」)。
3. **損失の表示**: 損失 = `Math.max(0, 開始評価 − 終了評価)`(`PracticeMode.tsx` 1275行付近、`stageStarJudge.ts` 55行)。評価が改善した場合は0にクランプされ、「-3→+2(損失0石)」という誤解を招く表示になる。

関連箇所:
- 開始評価 A: `PracticeMode.tsx` 616-618行付近(1手目着手前局面の全手解析の `best.discDiff` を `startEvalRef` に保存)
- 終了評価 B: `checkSessionEnd`(471-491行付近)が3往復後のユーザー手番局面を `getAnalyzedMoves` で再解析
- 各手の値: 526-531行、626-633行付近
- グラフ呼び出し: 1020-1021行付近

中盤練習の解析設定は `MIDGAME_ANALYZE_LIMIT = { depth: 10, timeMs: 10000, maxNodes: 2400000, exactFromEmpties: 24 }`。T201の経緯・品質測定は `tasks/T201-midgame-deterministic-judge.md` を参照。品質測定スクリプトとデータは `logs/t201/`(`tmp_t201_quality_measure.mjs`、resume対応、局面ごとJSONL追記)にある。

## 変更対象
- `engine/src/search.rs`・`engine/src/protocol.rs` — allMoves+maxNodes 経路で採用する完走ラウンドの深さの偶奇を、`limit.depth` の偶奇に揃える(例: depth=10 なら偶数深さの完走ラウンドのみ採用)。奇数ラウンドを move ordering・TT のために探索するかどうかは実装者の判断でよい(品質と時間で決める)。
- `app/src/midgame/PracticeMode.tsx` — 結果画面のグラフ点の算出元、評価値・損失の文言。
- `app/src/components/moveEvalTimeline.ts`(必要なら `EvalGraph.tsx`) — 開始値・点の差し替えに対応する引数を追加する。**対局モード・棋譜解析など他の呼び出し元の表示は変えない**(引数省略時は従来挙動)。
- テスト: engine(cargo test)・app(vitest、`PracticeMode.flow.test.tsx` 流儀で `requestAnalyzeAll` をモック)。

## 要件
1. **偶奇の統一(engine)**: allMoves+maxNodes の結果は、常に `limit.depth` と同じ偶奇の深さで完走したラウンドの値になる。決定性(T201の要件。同一入力ならビット同一)は維持する。maxNodes 未指定の経路、exactFromEmpties 以下の完全読み経路、他モードの挙動は変えない。
2. **グラフはすべてユーザー手番局面の根解析基準にする(app)**: 中盤練習の結果グラフの点を次の値にする(すべてユーザー視点。下記6参照)。
   - 1点目 = 開始評価 A(開始局面の根解析の最善値)
   - ユーザーの手の点 = その局面の根解析での打った手の値(現行どおり)
   - 相手の応手の点 = **応手後のユーザー手番局面の根解析の最善値**(次の手のために必ず解析している値を再利用する。相手手番局面の解析値は使わない)。3回目の応手の点 = 終了評価 B
   - これにより、グラフの最終点と「→ B」の表示が一致し、全点が同じ偶奇の深さの値になる。
3. **損失・評価値の文言**: 「評価値 A → B」は維持する。損失が正なら「(損失n石)」、開始より改善した場合は「(開始より n 石改善)」のように、クランプされた0を誤解させない表現にする(★判定式・閾値は変えない)。
4. **グラフの説明**: 結果グラフの近くに短い説明を添える(例:「各手を打った後のあなた視点の評価値。最後の点は相手の3手目の応手後」)。文言は簡潔に。
5. **品質の再測定**: T201の38局面(ステージ 1,4,7,…,109 と問題86)で、偶奇統一後の方式について、参照最善手との一致率・平均/最大regret・解析時間(通常時の平均/最大)を測り、T201の表(旧: 一致25/38・平均0.37・最大2.66・730/822ms、T201方式: 25/38・0.46・3.88・779/1288ms)と並べて作業ログに記録する。偶奇を揃えた結果、予算240万で多くの局面が深さ8止まりになって品質が落ちる場合は、予算を調整してよい(通常時平均1秒前後・最大1.5秒程度が目安)。予算値の根拠を作業ログに記録。測定は局面ごとに `logs/t201/`(または `logs/t202/`)へ逐次追記し、resume可能にすること。
6. **視点**: 中盤練習の結果グラフはユーザー視点(ユーザーが白のステージでは黒視点から反転)で表示し、「評価値 A → B」と同じ視点にする。共有コンポーネントの既定(黒視点)は他モードのために維持する。
7. **回帰テスト(必須)**:
   - engine: allMoves+maxNodes で、予算が奇数深さの途中までしか届かないケースを含め、採用深さの偶奇が `limit.depth` と一致することを検証する(応答に完走深さを出すか、テスト用の内部関数で確認)。決定性(2回一致)も維持。
   - app: モックで「開始最善 -3、各ユーザー手番局面の最善値を指定」し、グラフの点列が要件2どおり(1点目=A、相手応手の点=応手後のユーザー局面の最善値、最終点=B)になることを検証する。損失が負のとき「改善」文言、正のとき「損失n石」になることも検証する。白番ステージでグラフがユーザー視点に反転されることも検証する。
   - 問題86の f2 → (応手) → f1 → (応手) → e1 → (応手) を本番設定で通し、グラフ最終点と B が一致し、2回通しても同一になることを Rust または node+wasm テストで確認する(重いテストは CI の debug でも壁時計保険にかからない timeMs にすること。T201でCIのdebugビルドが60秒の保険に掛かって失敗した前例あり)。
8. 作業ログに: 偶奇統一の実装方式、品質測定表、問題86(f2/f1/e1 と g6/f2/h5 の2手順)の A・B・グラフ点列・★を記録する。
